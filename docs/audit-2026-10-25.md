# VeilDesk by PolyDesk — implementation audit

Scope: local envelope encryption, payment adapter, mandate authorization, local replay ledger and PolyDesk integration surface. This is a development review, not an independent security certification.

## Fixed

- Encrypted payloads alone did not identify a sender. Added signed payloads binding protocol domain, request ID, direction and recipient encryption key; verify against a pinned signing key.
- Loose confirmation comparison could accept missing/non-numeric confirmation counts. Require an integer confirmation count and a valid block hash.
- Invoice expiry prevented discovery of real incoming money. Continue receipt inspection and distinguish late_payment_review from expired_unpaid. Late payments never imply execution authorization.
- Send approval accepted arbitrary truthy values. Require boolean true and validate the full invoice before RPC calls.
- Mandates lacked an execution/replay boundary. Added strict preview-only mandate validation and durable reservations before work. Uncertain/crashed work is not automatically retried.

## Demonstrated

Run `node scripts/demo.mjs`. Separate requester/provider processes authenticate encrypted messages, validate a bounded dry-run mandate, return an authenticated encrypted receipt and retrieve the same receipt on replay. The demo uses a synthetic market and sends no funds or trades. Keys are bootstrapped through a locally owned child-process channel. This is not remote identity discovery.

## Still blocks production

- No verified real Zcash wallet connection or shielded testnet settlement. Address validation, wallet compatibility, asynchronous send completion, durable payment-note redemption and reorg handling remain unfinished.
- Payment receipt verification is not wired to mandate execution. There is no live execution adapter. Preview authorization can never authorize real trading.
- Local filesystem reservations are single-host only. Crash recovery, directory durability, key recovery/rotation, retention and distributed locking require further work.
- Remote key authentication and provider enrollment are not implemented. The signing/encryption construction requires independent review before customer use.
- No OKX VeilDesk listing. Native/external ZEC marketplace payment eligibility remains unconfirmed.
- Hackathon entry eligibility and prize funding must be confirmed with organizers. Public source includes placeholder prize-allocation comments. A community announcement is corroboration of publicity, not verification of funded prizes.

## Privacy boundary

The provider sees the authorized mandate after decryption. Stable signing keys, IP addresses, timing and traffic volume can correlate activity. Receipt identifiers and filesystem metadata also reveal activity. Public Polymarket fills and holdings are not made private. Do not submit plaintext mandates in marketplace chat or treat transport encryption as anonymous execution.

## 2026-10-26 continuation

Implemented a separate testnet-only Zallet receipt verifier using the installed
wallet's OpenRPC schemas. Recipient evidence includes account UUID, exact address,
external incoming note, integer zatoshis, memo and pool-specific index. Verification
also checks sync, wallet mining status, Zebra transaction shape, confirmations,
height and canonical block hash, with a stable-tip recheck. Signed preview mandates
are durably bound to invoices; note reservations prevent cross-binding reuse and
secondary notes require duplicate review. Replays reverify and changed block hashes
require reorg review. All receipts retain `executionAuthorized: false`.

These are fixture-tested implementation changes, not proof of shielded settlement.
The live readiness gate was exercised and rejected the still-syncing services.
Zebra reached 15,200 and Zallet 12,310 during this check; no account/faucet/payment,
trade, deployment or listing was completed. See testnet-setup.md for exact remaining
acceptance and conservative transaction-version/address limitations. Existing audit
production blockers still apply; the legacy adapter remains unwired.

## v0.2 paid-lifecycle audit notes

The optional testnet-paid capability persists its invoice and authenticated mandate
binding, accepts one signed encrypted txid hint, reserves a note before constructing
a result, and rechecks note/finality/deadlines before delivery. Reorg/duplicate/late
states become immutable signed review notices and block delivery. Client-side
amount caps and original mandate digest checks remain mandatory. No wallet sends
or refunds are implemented by this service. Default provisioning stays unpaid.

New acceptance evidence is HTTP integration against synthetic wallet RPC replies.
It is not a live Zcash settlement test. Invoice admission now fails closed for
unknown or newer consensus branches (including active NU7). Current-format support,
owned-address setup, live note evidence and deployed operation remain release gates.
A delivered encrypted result cannot be recalled following a later reorg. Manual
review, refund policy and continuous monitoring of late transfers are still needed
before customer use. See payment-lifecycle.md for exact behavior and limitations.

## Encrypted service checkpoint (2026-10-27)

Added authenticated encrypted directory checkpoints for stopped service state.
The local process test restores keys, relay database, provider records and client
outboxes to a new directory, then checks completed-result replay, queued delivery
and persistent revocation through real processes and PolyDesk's adapter. All 39
acceptance tests pass. This is same-host relocation evidence, not an independent
host disaster-recovery or real wallet backup drill. Operator inventory/quiescence,
rollback reconciliation, protected passwords and separate wallet recovery remain
necessary. See recovery-checkpoint.md for precise scope and constraints.

## Bounded load evidence (2026-10-27)

The separate relay process passed a paced 300-job workload at concurrency 10,
plus intentional pending/storage quota failures and restart verification of all
364 stored records. No unexpected HTTP failure occurred. See load-acceptance.md
and its source-hashed report for methodology, latency and limitations. Production
polling-worker throughput, long soak, shutdown under traffic and edge protections
are not established by this run. No wallet or public service was contacted.

## HTTP body and drain hardening (2026-10-27)

Fixed a streaming resource gap: the previous 16 KiB buffer limit still consumed
an unlimited upload before returning 413. Oversized declared/chunked bodies now
fail early, stalled body reads have a bounded deadline, and incomplete error
connections close. Tests verify healthy admission after rejection and shutdown
with concurrent valid/stalled uploads. The committed job survives restart and
replay. Reverse-proxy deployment and distributed-flood controls remain unverified.
